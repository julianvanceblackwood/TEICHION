# TEICHION Generation-0 Threat Model

## Purpose

This document defines the security boundary that exists **today** in Generation 0.

It does not describe future cryptographic, transport, key-management, persistence, or physical-hardware properties as though they already exist.

## System under analysis

Generation 0 consists of:

- `rtl/core/teichion_seal_chain.sv`;
- `tb/core/teichion_seal_chain_tb.sv`;
- the associated Verilator verification workflow.

The Generation-0 controller owns deterministic chain-state sequencing around an externally supplied tag result.

It does not yet own cryptographic tag generation.

## Protected state

Generation 0 contains security-relevant state for:

- next sequence value;
- pending sequence value;
- previous accepted tag;
- pending previous tag;
- receipt sequence;
- receipt tag;
- controller transaction state.

The integrity of these state transitions is the primary Generation-0 concern.

## Trust zones

### Zone A: Host / upstream requester

Generation 0 does not trust the host to define chain ordering.

The host or upstream environment may control request timing.

Future host-originated record content is expected to be untrusted until accepted through a defined canonical framing boundary.

### Zone B: Generation-0 controller

The current RTL controller owns:

- sequence allocation;
- capture of previous-tag context;
- transaction progression;
- receipt holding behavior.

This is the implemented Generation-0 trust primitive.

### Zone C: External tag producer

The current `tag_i` and `tag_valid_i` interface is outside the Generation-0 cryptographic trust boundary.

Generation 0 accepts the provided tag as a transaction result for the purpose of exercising chain-state semantics.

Therefore:

> Generation 0 does not prove that `tag_i` is authentic, secret-derived, collision resistant, or generated by trusted hardware.

A future cryptographic engine must replace this assumption before hardware-sealed authenticity can be claimed.

### Zone D: Downstream receipt consumer

The downstream consumer may apply backpressure through `receipt_ready_i`.

Generation 0 is expected to preserve the externally visible receipt while stalled.

The downstream consumer is not currently modeled as a trusted persistent verifier.

## Attacker capabilities considered

For Generation 0, a hostile or faulty surrounding environment may be able to:

- assert requests at adversarial times;
- delay context acceptance;
- delay receipt acceptance;
- provide arbitrary tag values;
- choose when `tag_valid_i` is asserted;
- reset or power-cycle the design through the external reset boundary;
- replay higher-level host events outside the current RTL interface;
- suppress events before they ever reach TEICHION.

These capabilities are not all mitigated in Generation 0.

The threat model distinguishes what is exercised from what remains unresolved.

## Verified properties

Current automated verification provides evidence for the following properties under the exercised conditions.

### Explicit genesis

Reset establishes:

```text
sequence       = 0
previous tag   = 0
pending state  = 0
receipt state  = 0
controller     = IDLE
```

### Reset-epoch sequence progression

Within one uninterrupted reset epoch, accepted transactions receive sequential 64-bit sequence values beginning at zero.

This is not a persistent monotonic counter across reset.

### Previous-tag propagation

After a tag result is accepted, the next transaction context observes that accepted tag as its previous-tag value.

### Receipt stability under backpressure

While `receipt_valid_o` is asserted and `receipt_ready_i` remains deasserted, the receipt sequence and receipt tag remain stable under the current test.

### Single transaction in flight

Generation 0 does not accept a new request while the current transaction is in context delivery, tag wait, or receipt hold.

### Return to acceptance

After the receipt handshake completes, the controller returns to the request-accepting state.

## Important non-properties

Generation 0 does **not** establish the following properties.

### Cryptographic authenticity

Because `tag_i` is externally supplied, Generation 0 cannot establish that a receipt tag was produced by HMAC-SHA-256, by a protected key, or by trusted hardware.

### Event completeness

If an event never reaches the FPGA boundary, Generation 0 cannot prove whether:

- the event never occurred;
- the host failed to observe it;
- the host suppressed it;
- transport dropped it;
- an upstream component failed.

Therefore:

```text
absence of a TEICHION receipt
            !=
proof of event non-occurrence
```

### Persistent anti-rollback

Reset returns the sequence and previous-tag state to genesis.

Generation 0 does not resist rollback caused by:

- reset;
- power loss;
- state restoration;
- malicious restart.

### Sequence-exhaustion policy

The sequence register is 64 bits.

Generation 0 does not yet define production behavior for sequence exhaustion or wraparound.

A hardened design must choose explicit behavior rather than relying on accidental modulo arithmetic.

### Protected key storage

No device secret or key lifecycle exists in Generation 0.

### Physical FPGA security

Generation 0 makes no claim regarding:

- secure boot;
- authenticated bitstreams;
- eFuse / BBRAM key protection;
- debug-port exposure;
- fault injection;
- side channels;
- probing;
- supply-chain compromise.

### Independent verification

The current testbench validates controller behavior but is not yet an independent receipt verifier operating from a canonical wire representation.

## Reset threat

Reset is one of the most important unresolved security boundaries.

The current reset behavior is deterministic and useful for verification, but a future persistent chain must distinguish among:

- first boot;
- expected reboot;
- unexpected reset;
- power interruption;
- rollback attempt;
- forked chain;
- restored hardware state.

Before TEICHION claims persistent ordering, the design must bind chain continuity to an authenticated epoch or other protected persistence mechanism.

## Backpressure threat

Backpressure can create state-holding conditions that frequently expose handshake bugs.

Generation 0 currently verifies receipt stability during downstream stall.

Future verification should expand this reasoning to:

- context backpressure over longer randomized windows;
- adversarial handshake timing;
- reset during each transaction state;
- malformed or repeated tag-valid behavior;
- sequence-boundary conditions.

## Future cryptographic boundary

Before TEICHION promotes hardware-sealed authenticity from TARGET to VERIFIED, the threat model must be updated to define at least:

- canonical authenticated bytes;
- framing and length rules;
- domain separation;
- sequence encoding and byte order;
- epoch encoding;
- previous-seal inclusion;
- HMAC key ownership;
- key provisioning;
- key zeroization;
- reset behavior;
- malformed-input behavior;
- verifier behavior;
- persistent-state assumptions.

## Future host boundary

A future host transport must assume that a compromised host may:

- forge record contents;
- replay old records;
- reorder submissions;
- submit malformed frames;
- stall transport;
- disconnect;
- lie about timestamps;
- lie about process identity;
- suppress events entirely.

The FPGA boundary must only claim properties that remain meaningful under those capabilities.

## Review triggers

This threat model MUST be reviewed when a change affects:

- state ownership;
- reset semantics;
- sequence or epoch behavior;
- acceptance semantics;
- tag generation;
- canonical serialization;
- key material;
- persistent storage;
- host transport;
- independent verification;
- physical FPGA trust.

## Current security statement

The strongest defensible Generation-0 statement is:

> Within one reset epoch, TEICHION's current single-transaction RTL controller provides deterministic chain-state sequencing semantics around an externally supplied tag result and preserves receipt state under exercised backpressure conditions.

Anything stronger requires additional implementation and evidence.
